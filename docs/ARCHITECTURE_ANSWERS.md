# 架构设计：五个模块，各选一道

选择：**一-2、二-1、三-1、四-2、五-2**。以下是设计方案，不声称全部已在最小工程实现。

## 一 · 题 2：200 轮对话如何压缩，保持流畅

**按信息价值与 token 预算压缩，不按轮数硬切，也不把递归摘要当唯一真相。** 上下文分为：不可压缩的规则与目标、结构化任务账本、旧对话摘要、近期原文。接近输入预算约 70% 时准备压缩，预留生成和工具结果空间；70% 是待压测的起点，不是通用常数。

摘要采用固定结构：目标、约束、已确认事实、决定及理由、未决事项、下一步；每条关键事实带原始消息 ID。最近若干完整 turn 保留原文，工具调用/结果成组保留；大型工具输出外置，只留摘要与检索指针。关键数字、用户否定、权限和代码位置不能只靠自由转述。

候选摘要先校验目标/约束锚点与证据；缺失或冲突就不切换，缩小压缩范围重试。通过后原子更新摘要版本，原文不删。“刚才那个参数”优先近期原文，“上个月为什么选 A”按引用取回旧原文；查不到就澄清，不补故事。

**取舍**：压缩额外消耗一次推理，少数回查增加延迟；保留太多又失去收益。用成对任务比较压缩前后跨轮指代、数字、用户纠正和工具配对，度量约束保留率、任务成功率、token 降幅和 p95 延迟，不能只评“摘要通顺”。

本工程只做完整 turn 的预算裁剪和持久化，**没有实现上述语义压缩**。

## 二 · 题 1：半个月后重问旧问题，Memory 如何召回

**先判断问题是否依赖过去，再召回；重问不代表想听旧答案。** “上次选了哪家”“按之前口味”需要个人历史；纯算术默认不检索个人档案。旧回答可能已经过时，必须区分“过去怎么说”和“现在应该怎么做”。

记忆分显式偏好、可追溯事件、历史问答索引，包含 user_id、来源、时间、有效期、可见范围。先权限/删除过滤，再实体与关键词 + 向量混合召回，按相关性、时效、明确确认程度和当前任务重排、去重，只注入少量带时间/来源的证据，放独立 reference 区，不提升为系统指令。

稳定偏好可复用；天气、价格、政策等动态事实要刷新。旧“住上海”和新“搬到杭州”按生效时间及明确更新处理，不按向量分数一票决定。不确定时问一句，不能装作“当然记得”。删除传播到摘要、索引和召回缓存，不能只删源行。

**取舍与验收**：多阶段召回增加延迟，小数据先结构化索引，规模上来再加向量服务。建立该召回/不该召回、冲突、过期、跨用户、已删除测试集；测必要信息命中率、无关注入率、旧事实错误复用率，跨用户泄漏必须为 0。

本工程只实现显式偏好最近 8 条召回，**不是完整的半个月历史语义记忆**。

## 三 · 题 1：长程任务忘目标，怎么办

**目标应是版本化任务状态，而不是一条很快被挤走的聊天消息。** 任务包含 objective、constraints、acceptance、plan、current_step、evidence、next_action、version。每次决策重注入精简目标与当前步骤；完成与否由程序根据实际证据判断，不能让模型一句“完成了”替代验收。

| 方法 | 优点 | 代价/失效点 |
|---|---|---|
| 每步重注入目标/约束 | 便宜直接 | 占输入预算；不保证模型遵守 |
| 外置计划、checkpoint、证据账本 | 可断点续跑 | 若模型自由改写，可能把失败改写成成功 |
| 里程碑验证器/审阅 | 发现偏离与假完成 | 有成本；模型审阅可能共犯，优先可执行检查 |

三层组合，状态变更经受控接口；不是每一步都昂贵地“反思”。用户改目标生成新版本，旧工具结果带 goal_version，迟到结果不能覆盖新目标。连续同类失败或时间/成本超限就停止并报告具体阻塞，不无限循环。

恢复时读最后确认 checkpoint，先核对外部副作用，再执行首个未完成动作，不重放全部写操作。测试注入长干扰、目标修改、崩溃、重复失败与迟到结果，观察目标保持率、假完成率、重复副作用数和额外 token 成本。

本工程已有预算、回执和中断标记，**没有完整长程任务计划器**。

## 四 · 题 2：busy 时，新消息与异步结果同时到达

**每 session 一个持久化 mailbox 和单写者，不让 HTTP handler 随意改共享 messages。** 输入统一为事件，带 event_id、session_id、run_id、generation 和 session_seq。身份来自认证上下文，而不是客户端任意 user_id。

普通消息入队并立即确认收到；停止是控制事件，可优先在安全点生效。明确修改当前目标时先取消旧 generation，再新开 turn，不能把用户消息插进尚未补齐 tool result 的协议中间。

异步工具结果先验 job_id/run_id/generation、去重并写任务表。旧 run 已取消则标 late/orphaned，允许用户查看，但不偷偷唤醒别的 run。匹配当前等待集合才补对应 tool_call_id；同批调用全部配对或收到超时结果后才继续模型。并发事件按持久化 session_seq 排序，跨 session 无需全局序。

把 session 是否有执行者、run 生命周期、job 生命周期分开，不让一个 busy 字段承担全部含义。状态变更和 outbox 通知同事务提交；消息至少一次投递，event_id 幂等消费。恢复依赖 checkpoint/租约，外部副作用另有幂等键，不能因用了队列就宣称 exactly-once。

**取舍与验收**：持久化 actor 有存储/运维成本，但适合慢任务。测试两个事件顺序、重复、乱序、断线和宕机，保证不丢事件、不污染新 run、不重复写。本工程只有单进程 session gate 和等待式异步 I/O，**没有实现完整后台 job 系统**。

## 五 · 题 2：OpenHands 状态机优缺与改进

先限定版本：分析的是 [OpenHands 0.50.0 AgentController](https://github.com/OpenHands/OpenHands/blob/0.50.0/openhands/controller/agent_controller.py)。其职责包括 pending action、observation 关联、确认、状态迁移与保存、循环检测。官方 [v1 迁移说明](https://www.openhands.dev/blog/the-path-to-openhands-v1) 已提出拆分 SDK；[新 SDK ConversationState](https://github.com/OpenHands/software-agent-sdk/blob/main/openhands-sdk/openhands/sdk/conversation/state.py) 仍有 execution_status。因此不能把旧控制器等同于今天全部架构，也不能把改进说成“删掉状态机”。main 链接持续变化，核验日为 2026-10-21。

**我的分析**：显式生命周期方便暂停、确认、恢复和审计；动作与观察可关联。扩展风险在于状态切换同时重置、重发动作、发事件和保存，副作用多、转换难单测；多个异步任务让单枚举与单 pending action 的职责更重。这是扩展性判断，不声称原项目没有防护。

更合适的方式是保留有限状态机，将核心改为纯转换 `reduce(state,event) → (new_state,commands)`；executor 处理副作用并产生后续事件。session/run/job 使用正交状态，事件存储 + outbox + checkpoint 管恢复；模型提供决策建议，不能直接写 runtime 状态。

例如 ToolSucceeded 先更新 job，只有属于当前 run 等待集合才发 ContinueModel；不可逆命令带幂等键并经过权限门。优点是转换能表驱动测试、可重放；代价是事件版本迁移和运维复杂，小 Agent 不必提前分布式化。

验收穷举关键事件顺序，做性质测试：终态不因迟到结果重启、调用结果不重复消费、tool 消息无孤儿、重放状态一致。所谓优雅应体现为**可验证性**，不是类名更漂亮。
